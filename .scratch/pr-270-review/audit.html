Functional bugs to fix before merge

Verified by reading the scripts directly, not from the bot's findings.

Bug

Failed runs still exit 0

run-test.sh records FAIL(…) in summary.tsv and then exits 0 regardless. The batch loop in run-suite.sh does the same. Any --repeat 3 automation or CI step chained with && reports success after a failed recovery test.

Bug

The profile refactor broke the result helpers

check-latest-run.sh and summarize-all-runs.sh only look for openshift-two-node-suite-* directories. run-suite.sh now names sessions <profile>-suite-*, and run-test.sh defaults to tnf-two-node-*. The README's own quick-start commands produce runs these helpers can't find. Match on the presence of summary.tsv instead of a name prefix.

check-latest-run.sh:13summarize-all-runs.sh:20run-suite.sh:176
Bug

run-test.sh hardcodes the two-node suite

Both invocations of the test binary run openshift/two-node unconditionally. Interactive mode in run-suite.sh dispatches every profile through run-test.sh, so --interactive with e2e, dualreplica, or cert-rotation silently runs the wrong suite and matches nothing. The README recipe piping list-tests.sh --command-line into run-test.sh hits the same wall. Needs a --suite flag.

Bug

Two captures ignore CAPTURE_LOG_DIR

capture-virsh-status.sh and capture-baremetal-operator.sh hardcode scripts/debug while run-all-captures.sh reports the file as living in the run directory. run-all-captures.sh also never exports its own computed LOG_DIR as CAPTURE_LOG_DIR, so the documented standalone usage of these two scripts scatters output outside every run.

capture-virsh-status.sh:12capture-baremetal-operator.sh:12run-all-captures.sh:34-39
Bug

Same-day session reuse is fragile

A new invocation merges into any existing same-day session directory with a matching name, and iteration numbering restarts at 1 — colliding rows in summary.tsv. A suite crossing UTC midnight splits into two sessions instead. run-suite.sh should create the directory once and pass it down explicitly.

Hygiene and repo conventions

Not bugs on their own, but the kind of debt that makes the next PR harder to review.

Hygiene

"Generalized helpers" that the main runner doesn't use

run-test.sh reimplements ts, log, sanitize_name, matches_stop_pattern, hypervisor setup, and monitor config instead of sourcing test-helpers.sh. Separately, resolve_master_ip_from_leases is copy-pasted into five capture scripts, and the copies have already diverged: the "Hardening captures" commit added SSH keepalive/BatchMode options to three of them but missed two, which will hang instead of reconnecting on a half-open hypervisor hop.

Where to push back on CodeRabbit

All 52 threads are open and unresolved. Not all of them describe a real problem for this tool's actual threat model.

Push back

"Injection vectors" is overstated as a blocking severity

Every interpolated value is the operator's own environment — HYPERVISOR_IP, MASTER_SSH_USER, and lease-resolved IPs that already pass through an address-shaped regex in resolve_master_ip_from_leases. Reply with that reasoning rather than rewriting the SSH layer. One real concession closes the thread cheaply: the explicit MASTER_0_IP/MASTER_1_IP overrides bypass that regex entirely and should be validated against it too.

Push back

"Sensitive data in logs" describes the tool's purpose

Capturing raw cluster and host logs for diagnosis is what this tool exists to do, and every capture already lands under a gitignored runs/ directory (runs/, tests-bin/, scripts/debug/, *.log in .gitignore). State that explicitly in the PR description rather than building a sanitization pipeline.

Push back

StrictHostKeyChecking=no is a defensible default here

Flagged across five capture scripts. The hypervisor is an ephemeral EC2 instance whose host key changes on every redeploy, and the two-node-toolbox deploy pattern doesn't give operators a stable key to pin in advance. accept-new on the outer (local-to-hypervisor) hop is the honest middle ground: it pins the key for the session without ever prompting. The inner hop already uses UserKnownHostsFile=/dev/null against masters that are provisioned fresh on every run, so leave it as-is.

Push back

The proxy.env sourcing finding needs a correction

CodeRabbit's finding treats missing set -a as a bug on the assumption that this repo controls the file's format. It doesn't: proxy.env is generated by the two-node-toolbox submodule. Checked directly against upstream two-node-toolbox at its current main (commit ce6ed9e) — not the 160-commits-stale copy vendored in this repo — the generator still writes every variable with export, and the toolbox's own consumers (oc-wrapper.sh, deploy/common.sh, its documented Claude command workflows) rely on a plain source proxy.env. The export contract is load-bearing for the toolbox itself, so it isn't a property this PR can quietly assume away, and a defensive wrapper here wouldn't protect against it changing anyway.

That said, the branch does source proxy.env at five separate call sites using two different conventions — plain source in three, set -a/set +a in two — which is worth fixing for consistency, on its own terms rather than CodeRabbit's. Recommended fix: consolidate all five sites into test-helpers.sh's load_proxy_env, standardize on set -a to match the two sites that already use it, and add a post-source assertion that KUBECONFIG and EC2_PUBLIC_IP actually got set — two capture scripts already half-do this via oc whoami and a healthz probe. That catches real drift in the upstream format directly, instead of masking the dependency behind an export flag that gives no signal if the toolbox's contract ever changes.

One concrete cost of the coupling is worth naming separately, since nobody has: the generated file prints two informational lines and runs a kubeconfig-existence check every time it's sourced, and every capture script that sources it leaks that chatter into its evidence log.

Push back

Missing set -e in the reconnect-loop scripts is intentional

In capture-ovn-kubernetes-follow-logs.sh, capture-ovn-control-plane-follow-logs.sh, capture-network-node-identity-follow-logs.sh, and capture-ovn-chassis-trace.sh, every foreground command is expected to fail — an oc logs -f ends the moment its pod is deleted, which is the normal case during a recovery test, not an error. Keep set -uo pipefail only, and add a one-line comment stating why, which also satisfies CONTRIBUTING.md's intent without adopting the letter of the rule blindly.

Push back

Consolidate, don't fix seven times over

Poll-interval numeric validation is flagged as a separate finding on seven different scripts. One require_positive_int helper added to test-helpers.sh and called from each poll loop closes all seven at once. Similarly, the 80% docstring-coverage warning is a Python-oriented metric and isn't meaningful for bash scripts documented through header comments — note that in the PR description rather than writing docstring-shaped comments to game the number.
